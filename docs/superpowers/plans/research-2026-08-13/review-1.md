[1] [blocker] The per-session accent wheel and the state-tone vocabulary use the same hues, so identity color will be read as status color.
- Evidence: plan §5.1.2 + §9.1 propose "a curated 8-hue wheel **matching our status palette**"; §5.3 assigns semantics to exactly those hues (amber=working, blue=waiting, green=done, calm-orange=failed), which are the only 5 hues that exist (`web/src/styles/globals.css:94-98`). Grok deliberately gives agents hues *outside* its 4 semantic hues (teal/indigo/violet/orange-red — wfresult-4 §3.3) and confines accent to avatar, mention chip, side-pane 6% tint. A session hashing to blue would render a blue avatar + blue tints in a transcript where blue means "needs input" (`anim-hero-02.png` badge vs `anim-hero-08.png` badge).
- Fix: define the 8 accent hues explicitly disjoint from the 4 status hues (≥30° hue distance, assert it in a unit test on the wheel table), and add a disjointness rule to §5: accent may tint only avatar / mention chip / card-title hover underline / tile identity strip; tone tints only badges and the card's left edge — never the same surface. Also reuse the existing tone-badge implementation (`bg-status-error/15` + full-strength text, `web/src/components/session-tile/activity-status.tsx:113-119`) instead of introducing a second `color-mix(... 14%)` formulation.

[2] [blocker] No spec for the optimistic echo of the user's own prompt — the single most latency-visible micro-interaction in a chat UI is missing.
- Evidence: §2.3 sources the user prompt from the transcript at **flush** latency; §8 concedes flush latency is unknown until fase 0; §3 sends via `POST /send`. So Enter → nothing on screen for an unbounded interval, then a bubble pops in from below. Fase 3 mentions "queued messages shown as pending pills" but §5 has no spec for them at all.
- Fix: add a ninth primitive "pending user bubble" with three visual states (sending → sent-unconfirmed → failed/retry), the dedupe key used to reconcile against the transcript entry (`last_send_text` + timestamp window), and an explicit rule that reconciliation is a *no-op crossfade*, never a second entry-pop. Same treatment for steer/queued prompts sent while a turn is active.

[3] [major] Three of the "eight primitives (Grok-validated)" are not in Grok at all, and they are the most detail-hungry ones.
- Evidence: §4.2 claims Grok validation for the full vocabulary; wfresult-4 §6 (line 187) states verbatim: "no file tree, **no diff viewer**, no terminal pane, no token/cost meter, **no plan/todo checklist widget**, **no collapsible 'thinking' trace**". So primitives 7 (diff), 8 (todo) and the thinking-content disclosure have zero reference pixels; the only borrowed value is the terminal-theme diff foreground (§3.6). The repo has no diff renderer to reuse either (nothing under `web/src/components/files/` renders a diff).
- Fix: strip the Grok-validated claim for those three and spec them from scratch with numbers before fase 2: unified vs split, gutter width, hunk header treatment, line numbers on/off, intra-line word-diff on/off, wrap vs horizontal scroll on mobile, max-height px + fade height, whether a `Write` of a new file renders as all-add or as a collapsed file card; todo rows: height, checkbox glyph, done strike-through, and the reorder animation (framer `layout`) when TodoWrite rewrites the list.

[4] [major] Claude's dialogs are numbered choice lists; the plan flattens them into "action pills" and skips Grok's purpose-built choice-option widget.
- Evidence: real dialogs are `❯ 1. Yes / 2. No, and tell Claude what to do differently` (`server/src/sessions/status.rs:1183`, `server/src/sessions/lifecycle.rs:1696`). Grok ships `.baby-grok-bot-choice-option`: full-width 10px rows, `[data-selected]` = accent border 55% + accent fill 8%, a free-text `choice-input` (focus = accent border 55%) and a **Confirm pill at opacity .4 while disabled** (wfresult-4 §6.9). The plan's §4.2.4 card only has "action pills", losing selected-state, 1/2/3 keyboard parity with the TUI, and the free-text branch that Claude's third option literally requires.
- Fix: adopt choice-option as its own primitive for permission prompts, plan approval and the trust dialog; bind each row 1:1 to the modal-registry key mapping so what is highlighted and what is sent are the same object; render the free-text row as an inline composer that posts via `/paste` + the option key.

[5] [major] Receipt list is specified for Grok's volume (4 lines), not Claude's (30–100 tool calls/turn), and it adds emoji to a system that is deliberately icon-free.
- Evidence: `anim-hero-08.png`/`anim-hero-12.png` show exactly 4 receipts inside **one** bubble; wfresult-4 §6.6: "Tool name bold 600, arrow, result, `·`-separated counts. **No icons, no boxes**". Plan §4.2.3 writes `✓ **⚡ Bash** → cargo check · ok 4.2s` — emoji from the terminal-era `activity_label` taxonomy, which break the 14/20 baseline, render per-platform, and violate §5.1's own "four semantic hues only". Nothing specifies grouping, coalescing, capping or interleaving.
- Fix: (a) one receipt bubble per contiguous tool run, coalesce repeats (`Read ×12`), cap at N with "show all N" and virtualize above ~200; (b) define the *running* receipt line (Grok only ever shows completed ✓) — spinner glyph in the check slot, label from the PreToolUse hook, morph to ✓ with the scale-.4 pop; (c) replace emoji with a 12px monochrome icon set at `currentColor`, or with weight/tone alone.

[6] [major] Successful tool output has no rendering spec at all — only failures get one.
- Evidence: §4.2.3 gives failures "danger tone + expandable stderr tail"; nothing anywhere covers a successful Bash/Grep/Read result, which is what users actually read (cargo output, test summaries, git status). §2.3's table stops at "tool result".
- Fix: add a mono output block: JetBrainsMono 12.5/18, `--terminal-fg` over `--terminal-bg` (so it harmonises with the toggle, per wfresult-4 §13.9), max-height ~220px with a bottom fade + expand, copy affordance, ANSI passed through the existing `lib/ansi.ts` SGR parser; state which tools default-expand vs collapse.

[7] [major] Grok's alpha/hairline discipline is copied verbatim onto a true-black OLED base where it stops being visible.
- Evidence: §5.1 mandates "4–14% alpha fills, 0.5px hairlines". Grok's dark substrate is `#1c1c1c` editor / `#262626` elevated (wfresult-4 §3.2, `dark-hero-00.png` — bubbles clearly read against grey); supermux's dark background is `#0a0a0a` with `--card: #1c1c1e` (`web/src/styles/globals.css:103,107`). `#ffffff0a` on `#0a0a0a` is a ~1.5% luminance delta. Separately, 0.5px borders are safe on Grok's Apple-only ≥2× hardware but round unpredictably on DPR-1 desktop browsers, which supermux serves. Grok itself retuned rather than reused for a second surface (§11: the mobile palette is warmer/softer).
- Fix: pin the chat substrate to `--card` (not `--background`) or raise dark fills to 8–12%; add a `hairline` utility that is 0.5px only above `2dppx` and 1px below; add a contrast assertion for bubble-vs-substrate to the VR pass in both themes.

[8] [major] Entrance choreography will animate the entire seeded backlog, and backlog-prepend/follow-bottom scroll behaviour is unspecified.
- Evidence: §5.1.3 gives every arriving entry a 0.28s pop (0.42s "fresh"), while §5.3 only says the seed is hidden until `seed_done` then revealed pinned-to-bottom. Grok's actual mechanism is a `[data-fresh]` attribute gate plus a one-shot 1s `mount-fade` for the whole surface (wfresult-4 §7, lines 210-232). §4.2 promises "earlier messages on scroll-top" with no scroll-anchor rule — the DOM version of the scrollback-ownership failure class the plan claims to kill.
- Fix: seed entries mount with `animation: none`; only entries arriving after `seed_done` carry `data-fresh`; one 1s container mount-fade on attach; specify scrollTop restoration via scrollHeight delta on prepend, a follow-bottom threshold in px (~48), and re-anchoring while a bubble grows mid-turn.

[9] [major] Two unreconciled motion languages, plus a reduced-motion rule that contradicts an existing documented exception.
- Evidence: `web/src/lib/springs.ts:1-14` mandates framer-motion SwiftUI springs for **every** motion and stores eases as arrays; §5.1.3 introduces CSS `cubic-bezier` string curves and implies four more CSS keyframes (typing wave 1.3s, receipt-check, 2.4s spinner, 0.26s badge crossfade) with no rule for which system owns what. §5.1.3's blanket "`prefers-reduced-motion: animation:none` on every animation" contradicts `web/src/styles/globals.css:384-399`, which deliberately keeps functional spinners spinning under Reduce Motion. Also dropped from the evidence: the thinking **label** enters on its own slower curve (0.35s `cubic-bezier(.2,.8,.3,1)`, wfresult-4 §7) — that two-stage stagger is the signature of the row the plan calls primitive 6.
- Fix: state the ownership rule ("CSS keyframes for ambient/infinite + list entry; framer springs for layout, gesture and shared-element morphs"), export both new curves in array *and* CSS-string form from `springs.ts`, carve functional spinners out of the reduced-motion blanket, and add the label stagger to §5.1.3.

[10] [major] The toggle — the product's defining interaction — has no visual specification.
- Evidence: §4.1 and §5.2 define it only as "pure view state → **instant** both ways" + a segmented control and `T` hotkey. Swapping a 14/20 DOM transcript for an xterm grid in one frame is the most jarring moment in the product, and it is also the moment where the two views must read as one product. Grok's own answer exists (1s `mount-fade`, §7) and so does the harmonising palette (`--terminal-bg #0a0a0a` / `--terminal-fg #d7d1c9` / borders `#ffffff14`, diffs `#9ece6a`/`#f7768e`, wfresult-4 §3.6/§13.9); the repo already has shared-element morph infra (`::view-transition-group` tuning at `globals.css:363-371`).
- Fix: spec a ≤180ms crossfade with no layout shift (terminal keeps its buffer, chat keeps scroll position), a session header pill that persists across the switch via `view-transition-name`, and align `--terminal-fg/--terminal-bg` + the diff palette to the chat surface.

[11] [major] No hover/press/focus vocabulary for any primitive, and Grok's one hover micro-interaction is misread as static chrome.
- Evidence: §5.1.2 lists "card-title underline (1.5px, accent)" as a persistent identity device; in the source it is hover-only text-decoration on a clickable title (`button.baby-grok-bot-card-title:hover { text-decoration-color: var(--grok-bot-current-agent-accent); text-decoration-thickness: 1.5px }`, wfresult-4 §8.8). §5.1.3 gives one generic "hover/pressed: flat 0.12s background-color", but nothing defines receipt-line hover (expand? copy?), message-hover actions (copy / anchor / reveal timestamp), touch pressed states, or `:focus-visible` rings — on a keyboard-first tool whose users live on `T`/Esc/Enter.
- Fix: a per-primitive hover/press/focus table in §5; restore the accent underline as hover-only on the card title; specify `:focus-visible` using `--ring` and a 44pt touch/press state for every card action.

[12] [minor] Bubble internals are half-borrowed: an avatar Grok does not have, and a markdown pipeline tuned for documents.
- Evidence: §4.2.2 "consecutive bubbles stack without repeated avatar" implies a per-bubble avatar; in every capture (`anim-hero-00/02/08/12.png`, `dark-hero-00.png`, `mobel-mobilephonescreen.png`) **no bubble has an avatar** — identity lives in the header pill and the roster rows, and the mascot's ambient life (eyes, `transition: fill .6s`, wfresult-4 §8.1) is what carries it; the plan also never says what supermux's avatar actually *is* (initials? glyph? generated shape?). Separately §4.2.2 reuses `markdown-viewer.tsx`, which is explicitly built for documents (`max-w-[72ch]`, "generous vertical rhythm", README heading scale — `web/src/components/files/markdown-viewer.tsx:33-35`) and will wreck 14/20/-0.15px bubble density. Bubble radius, padding and max-width are also unspecified (Grok: r16, 10/12 padding).
- Fix: drop per-bubble avatars (keep them in the header pill, tiles and the thinking row) and define the avatar's form; ship a `variant="chat"` component map for the markdown pipeline (compact headings, tight lists, inline code as a 4%-fill 0.92em mono chip) and VR-test a bubble containing h2 + list + fenced code; state bubble radius/padding/max-width explicitly.

Sound after scrutiny: §5.3's state-visual rule (one `hue @ ~14% fill + full-strength text` across working/waiting/done/failed, calm-orange never red) matches both the Grok evidence and the existing repo convention, and the deliberate divergence to a `<textarea>` composer over Grok's `contenteditable` is correctly motivated by the IME failure class.
